OneBeer MuleSoft workflow

Use Mule without living inside Anypoint Studio.

This workflow adds Mule project detection, Maven/MUnit commands, DataWeave CLI helpers, local XML catalog support, APIKit navigation, optional Anypoint CLI wrappers, and guarded test/debug integrations to the OneBeer Neovim config.

Quick start

1. Open a Mule project

Detection looks for pom.xml, mule-artifact.json, and src/main/mule/. Mule-specific XML behavior only activates for buffers under src/main/mule/** or src/test/munit/**.

2. Check dependencies

:checkhealth onebeer

The Mule section reports Java, Maven, dw, LemMinX, Anypoint CLI v4, Node, and npm.

3. Run the tight loop

:MuleBuild
:MuleTest
:MuleDwValidate

Failures go to quickfix where possible. Successful commands stay quiet and focused.

Command reference

Command What it does Depends on
:MuleBuild [args] Runs Maven in the detected Mule project. Defaults to mvn package. Java, Maven
:MuleTest [selector] Runs MUnit through Maven. Pass a selector to map to -Dmunit.test=.... Java, Maven, MUnit config
:MuleTestNearest Finds the nearest <munit:test> in the current suite and runs that selector. Java, Maven, MUnit config
:MuleDwValidate Runs dw validate for the current DataWeave buffer. DataWeave CLI
:MuleDwRun Runs the current DataWeave buffer with dw run and opens scratch output. DataWeave CLI
:MuleDwRepl Opens dw repl in a terminal split. DataWeave CLI
:MuleGenerateCatalog Discovers local XSD targetNamespace mappings from project resources/Exchange-module paths and writes .onebeer/mule-catalog.xml for LemMinX. LemMinX for editor diagnostics
:MuleStatus {args} Runs explicit Anypoint CLI status/list-style arguments and displays the output. Anypoint CLI v4

Core workflows

Build and test Mule apps

:MuleBuild
:MuleBuild clean package
:MuleTest
:MuleTest api-test#api-main-test
:MuleTestNearest

Maven owns build and test semantics. OneBeer only chooses the project root, runs the command, and turns failures into quickfix entries where the output includes file and line data.

Work with DataWeave

:edit src/main/resources/dw/transform.dwl
:MuleDwValidate
:MuleDwRun
:MuleDwRepl

*.dwl files use the dataweave filetype. Validation and execution are delegated to dw, because there is no open, reliable DataWeave language server in this workflow.

Validate Mule XML locally

:MuleGenerateCatalog
:checkhealth vim.lsp

Mule XML remains normal xml. Mule-specific behavior is gated by project root and path checks, so generic XML files do not inherit Mule catalog settings. Generation refreshes an active project-local LemMinX client; when no client is active, the next project-local start picks up the catalog. If no local XSD mappings are found, the command reports that state instead of writing an empty catalog.

Navigate APIKit projects

The APIKit parser understands generated flow names such as get:\health:api-config and maps them back to local specs declared by apikit:config. Local RAML supports top-level and nested resource segments; local OpenAPI YAML supports paths entries and method lines.

Remote resource:: Exchange specs stay offline-only: navigation reports that a local file is required instead of fetching from Anypoint or resolving credentials.

Use Anypoint CLI explicitly

:MuleStatus runtime-mgr:application:describe my-app --output json
:MuleStatus runtime-mgr:application:describe my-app --output=json

OneBeer does not infer destructive targets. Pass the Anypoint CLI arguments you intend to run, and keep org, environment, and credentials configured in Anypoint CLI itself. JSON output parsing is enabled for --output json, --output=json, and -o json.

Troubleshooting

No Mule project detected

Confirm the buffer is inside a project with pom.xml, mule-artifact.json, and src/main/mule/. Generic XML files are intentionally ignored.

dw is missing

Install DataWeave CLI and re-run :checkhealth onebeer. DataWeave commands fail closed when dw is not executable.

Anypoint auth fails

Fix Anypoint CLI or Maven settings outside Neovim. OneBeer reports auth failures but never reads or stores credentials.

DAP is unavailable

Mule DAP support is guarded until a local JDWP smoke test proves the path. The existing Neotest DAP keymap must not imply Mule debug support by default.

What this deliberately does not do

This is not a clone of Studio's visual canvas, DataSense, Anypoint Code Builder, or closed Mule DX internals. It is a Neovim-native workflow around the source files and command-line tools you can actually own.

The module boundaries under lua/onebeer/mule/ are intentionally extraction-ready, but the first implementation lives inside OneBeer until the public API is stable.

:MuleGenerateCatalog intentionally does not extract Maven artifacts or fetch remote/private schemas.
