## Direction suggestions

- Treat the DAP seam as a future spike, not a user-facing integration, until a JDWP smoke test proves it locally. The current guard is honest, but it should stay out of day-to-day docs unless enabled by an explicit plan.
- Add command-callback smoke coverage after the higher-priority Neotest and DataWeave fixes land. The job modules are covered; the user commands themselves are not yet exercised as commands.

## Findings considered and rejected

- Generated HTML polish: leftover style rules and repeated smoke commands are cosmetic and lower leverage than editor workflow correctness.
- Security: no high-confidence security finding was identified. The Anypoint wrapper delegates credentials to Anypoint CLI and does not read or store secrets.
- Micro-performance: indexing and parser throughput are not high-leverage at this scale. The editor-blocking process wait is tracked separately as IMP-014 because it directly affects interaction latency.
- DataWeave modified-buffer and validation-cwd handling: potentially real, but no `dw` binary is installed in the audit environment and the current fixture contract cannot prove import-resolution semantics. Revisit with an authoritative CLI fixture before writing a fix plan.
- Broader XML index completeness: flow/config parsing remains intentionally small and most index collections have no user-facing consumer. Plan 012 hardens only the APIKit declarations needed by the new command.
- Explicit destructive Anypoint arguments: by design. `MuleStatus` forwards only arguments the user typed and does not infer a target or read credentials.
- Full Mule JDWP support: still deferred until a real Java DAP adapter and local runtime smoke prove feasibility. Plan 011 only makes unsupported debug requests fail closed.

## Dependency notes

- Before dispatching any plan from 009 onward into an isolated worktree, commit the current Mule baseline. The product and docs are still untracked/modified in the audit checkout, and worktrees do not inherit that state.
- The `git diff --stat 5d80f88` drift command is informational because the Mule baseline was untracked when these plans were written. The authoritative gate is a committed baseline plus comparison of each plan's current-state contracts against live code.
- 009 is the verification prerequisite so every later plan has one complete Mule regression command.
- 013 follows 009 and owns the explicit catalog-write and command-output boundary contracts.
- 010 follows 013 because both plans edit `generate_catalog()`; 010 must preserve 013's failure handling and add the LemMinX refresh only after a confirmed catalog write.
- 011 and 012 are logically independent after 009, but plans 010-014 share `lua/onebeer/mule/smoke.lua`, command/docs surfaces, or both. Develop them in isolated branches if useful, then rebase and integrate one at a time in this order: 013, 010, 011, 012, 014.
- After each integration, rerun `smoke.run("all")`. Regenerate `doc/tags` from the integrated tree instead of hand-merging generated tag conflicts.
- 014 integrates last because the async refactor must preserve the hardened output/filesystem contracts and all commands added or changed by the preceding plans.
